Every Record Has a Home

Imagine a reliquary. Each compartment holds a complete set of information — name, age, city, role. A database table works the same way. Each row is a compartment. Each column is a field.

When you search for "Alice," the database does not read every compartment. It uses an index — like a catalog — to jump directly to the right place in O(log n) time.

Did You Know?
The world's largest database, Google's search index, contains over 100 trillion records. Finding one takes less than a second.
Exhibit 02

The Unbreakable Vault

Every trustworthy database swears a four-part oath. Click each pillar to discover the real-world promise behind the technical term.

A

Atomicity

All operations complete, or none do. There is no middle ground.

The Promise

Like a bank transfer: if the withdrawal works but the deposit fails, the entire transaction is cancelled. No partial updates allowed.

Real world: Buying a house. You do not get the keys unless every document is signed and every payment clears.
C

Consistency

The database never breaks its own rules. Every state is valid.

The Promise

If a column must be unique, it stays unique. If a balance cannot be negative, it never goes below zero.

Real world: A concert venue. The system never allows more tickets to be sold than seats exist.
I

Isolation

Your transaction is invisible to others until it is complete.

The Promise

Other users see the old data until you finish. It is like having a private conversation in a crowded room.

Real world: Editing a shared document. Colleagues see your changes only when you click "Save."
D

Durability

Once committed, data survives any catastrophe.

The Promise

Power outages, crashes, disasters — your data endures. Like carving in stone, not writing in sand.

Real world: A signed contract in a fireproof safe. It exists even if the building loses electricity.

Exhibit 06

The Index

The secret behind every fast database lookup. Plant keys into the tree and watch it grow, split, and self-balance — the algorithm that powers billions of searches per second.

Plant a Key

A B-Tree keeps data sorted and allows searches, insertions, and deletions in logarithmic time. When a node overflows, it splits and propagates upward.

Why B-Trees?
A B-Tree with 3 levels and 1,000 keys per node can locate any record among 1 billion items in just 3 disk reads.

Exhibit 14

The Forge

Raw data is messy. Normalization is the forge that refines it — splitting one chaotic table into many clean, purposeful ones.

Denormalized Table (Before)

OrderIDCustomerCustomerEmailProductCategoryQty
1Alicealice@example.comLaptopElectronics1
2Bobbob@example.comMouseElectronics2
3Alicealice@example.comKeyboardElectronics1

Third Normal Form (3NF)

We split into three tables: Customers (no repeating emails), Products (category lives here), and Orders (only IDs reference the others). Redundancy is eliminated. Updates require changing one place only.
